现在最危险的一句话是：

> 把任务交给 Agent，它会自己完成。

听起来像雇了一个 24 小时不下班、不要工资、还能同时开十个线程的员工。

但真实情况通常更接近另一种画面：

一个聪明、勤奋、理解速度很快的实习生，第一次进公司，没有权限意识，不了解历史包袱，不知道谁说话算数，也不明白“差不多做完”和“可以上线”之间隔着什么。

他不是不努力。

他只是没人带。

## 一、Agent 最擅长执行，最不擅长兜底

AI Agent 给人的第一印象，通常是“它真的会自己做事”。

它会读文件、调用接口、查资料、修改代码、运行命令，甚至在失败后继续尝试。

从演示角度看，这非常震撼。

但从工程角度看，最重要的从来不是“它能不能开始”，而是：

**失败之后，系统会变成什么样？**

一次自动化任务失败，可能只是返回一个错误。

一次 Agent 任务失败，可能是：

- 改错了一组文件
- 删除或覆盖了有效数据
- 调用了不该调用的接口
- 把敏感信息发送到外部服务
- 连续重试导致费用暴涨
- 表面任务成功，实际结果无法验证

普通程序按照写死的逻辑执行。

Agent 会在模糊环境里不断做选择。

这既是它的能力，也是它的风险。

## 二、Demo 很惊艳，生产环境只看五件事

很多 Agent 演示看起来无所不能，因为演示只回答一个问题：

> 顺利情况下，它能不能完成？

真实系统必须回答另外五个问题。

### 1. 输入是否可验证

如果任务目标本身含糊，Agent 只能猜。

“把网站体验优化一下”不是一个任务，是一句愿望。

“把首页首屏加载时间从 3 秒降到 1.5 秒以内，并保持现有功能不变”才接近可执行目标。

### 2. 权限边界是否清晰

不要因为 Agent 能访问数据库，就把生产库账号给它。

能力越大，越要遵循最小权限原则：

- 只能读，就不要给写权限
- 只能操作测试环境，就不要接触生产环境
- 只能修改指定目录，就不要开放整个仓库
- 涉及支付、删除、发布等动作，必须有人工确认

安全不是限制智能，而是限制破坏半径。

### 3. 失败是否可恢复

一个可靠的 Agent 工作流，必须允许失败。

它应该：

- 在独立分支或临时环境工作
- 产生可审查的中间结果
- 支持重试
- 支持撤销
- 在所有自动步骤失败后，留下足够信息让人接手

如果一次失败只能靠重新做人，那这套自动化就不适合生产。

### 4. 结果是否可审计

“它说自己完成了”不等于完成。

每一个关键动作都应该留下记录：

- 读取了哪些数据
- 调用了哪些工具
- 修改了哪些文件
- 为什么做出这个决定
- 用了哪个模型和提示词
- 总耗时和总成本是多少

日志不是为了形式上的透明，而是为了当结果出错时，我们还能找到原因。

### 5. 成本是否可预测

Agent 很容易陷入“再试一次”的循环。

Token 成本、工具调用成本、外部 API 成本和人工复核成本，都可能随着自主性快速上升。

真正适合 Agent 的任务，不只是它能做，还要满足：

**完成任务的收益，稳定高于验证和纠错的成本。**

## 三、别问 Agent 能做什么，先问任务如何验收

判断一个任务是否适合交给 Agent，可以看四个条件：

| 条件 | 适合交给 Agent | 不适合直接交给 Agent |
| --- | --- | --- |
| 目标 | 清晰、可量化 | 模糊、经常变化 |
| 环境 | 可隔离、可回滚 | 直接操作生产核心系统 |
| 结果 | 可自动检查 | 只能靠感觉判断 |
| 权限 | 范围有限 | 涉及高风险数据或动作 |

最简单的判断方法是：

> 你能不能设计出一套自动验收标准？

如果可以，Agent 会有很大价值。

如果最后仍然只能靠某个人打开页面看一眼，然后说“感觉还行”，那它最多只能辅助这个环节，不能独立负责整个流程。

## 四、一个靠谱的 Agent 工作流长什么样

不要把 Agent 想成一个孤立的超级员工。

更合理的结构，是把它放进一条有边界、有反馈、有闸门的工作流。

### 第一步：定义目标和禁区

除了写“要做什么”，还要写清楚：

- 绝对不能做什么
- 出现哪些情况必须停下来
- 哪些决定必须由人确认
- 什么结果才算完成

### 第二步：提供最小但足够的上下文

上下文太少，Agent 会猜。

上下文太多，关键信息又会被噪音淹没。

更好的方式是提供：

- 当前状态
- 最终目标
- 相关规则
- 已有约束
- 可参考案例

而不是一次性倒入整个知识库。

### 第三步：拆分任务并保留中间产物

让 Agent 完成一个小闭环，再进入下一个。

例如修改一个功能，可以分为：

1. 定位相关代码和测试
2. 给出修改方案
3. 实施最小改动
4. 运行测试
5. 总结风险和回滚方式

每一步都能检查，错误就不会一路放大。

### 第四步：自动验证，而不是自我评价

Agent 说“已经修复”没有意义。

测试通过、类型检查通过、构建成功、接口响应正确、指标恢复，才是证据。

如果没有自动验证，就让 Agent 生成一份专门的验证清单，交给另一个人执行。

### 第五步：在高风险动作前设置人工闸门

可以自动读，不一定自动写。

可以自动写草稿，不一定自动发布。

可以自动创建合并请求，不一定自动合并。

可以自动尝试修复，不一定自动操作生产。

**自主性应该逐步释放，而不是一次性全部交出去。**

## 五、Agent 不会消灭工作，它会把工作推向上下游

如果 Agent 接管了中间的“执行”，人的工作会去哪里？

通常会被推向两端。

上游是：

- 理解真实需求
- 定义成功标准
- 设计系统边界
- 拆解任务
- 准备可靠上下文

下游是：

- 审查结果
- 验证风险
- 处理异常
- 对最终结果负责
- 把一次经验沉淀成流程

这仍然需要大量工作，而且很多工作比原来的重复执行更难。

未来的核心能力，可能不是“会不会写提示词”，而是：

- 能不能把混乱问题整理成清晰流程
- 能不能设计合理的自动化边界
- 能不能建立验证与反馈机制
- 能不能判断什么时候不该让 AI 继续做

## 最后

AI Agent 的潜力很大，但它不是魔法，也不会因为叫“Agent”就自动获得责任感。

它真正的能力上限，不只取决于模型有多聪明，还取决于我们能不能把它放进一套：

**可执行、可验证、可审计、可回滚的工作流。**

所以，先别急着给它招聘邮件。

把它当成实习生，从低风险任务开始，给它清晰的边界，耐心的反馈，以及随时能够叫停的机制。

等它能稳定通过验收，再考虑给它更大的权限。

这才是从 Demo 走向生产的第一步。
